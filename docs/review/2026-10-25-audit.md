## Findings

### N1 / P3 — A failed obstacle retry re-searches on the next frame after a boost

**FIXED 2026-10-25** as described under Change. Re-measured on the committed code: 0 bursts on all three
seeds, placements 111 / 115 / 109; `check.sh --full` 14/14.

**Evidence (code).** `obstacle_spawner.gd:264` withholds scheduling while the player boosts, so
`next_pattern_time` falls behind real time (a trick boost is 3 s). A glide does the same for floating
patterns. When the overdue slot then fails the footprint guard, `:311` does
`next_pattern_time += FOOTPRINT_RETRY_DELAY`. That is still in the past, so the full forward search
(up to 13 starts, plus a solo fallback for a combo) runs again the next frame, and again, until it
catches up. `:297` (the first-appearance pause) has the same shape, and swallows the tutorial's
+1.5 s lead-in when it fires late.

**Evidence (measured).** Throwaway probe in a scratch copy, not committed: main scene, chasms and
powerup spawns off, the player re-shielded every frame so it survives, a speed boost forced every
10 s, `schedule_pattern()` timed per call. Seeds 683407368, 941462462 and 2033395789, 10 min each:

| | Bursts of back-to-back searches | Longest | Extra search time | Patterns placed |
|---|---:|---:|---:|---:|
| As shipped | 2 / 6 / 6 | 3 frames | 1.4 / 2.3 / 4.4 ms | 114 / 117 / 115 |
| Both lines retry from `elapsed_time` | 0 / 0 / 0 | 1 | 0 | 111 / 115 / 109 |

No boosts (control, seed 683407368, 5 min): 0 bursts. Timings are this container's CPU, not a phone's.
A boost every 10 s is a heavy trick cadence, so these counts are an upper end for real play.

**Change.** Retry from now: `next_pattern_time = elapsed_time + FOOTPRINT_RETRY_DELAY` at `:311`, and
the same form for `FIRST_APPEARANCE_EXTRA_ROOM` at `:297`. Density drops ~3–5%, because a retry now
really waits a second.

**Done when** `check.sh` passes and the probe shows 0 bursts. Small on its own; it matters mostly because
A3 (below) is about exactly this search's cost.

### N2 / P2 (process) — Every phone number so far comes from a debug export

**Evidence.** The documented export is `--export-debug` (`debugging.md`, "Android device testing"). In
any debug build: `DEBUG_SHOW_PLAYER_STATE` and `DEBUG_LOG_FREEZE_REPRO` (`player.gd:154–155`) draw the
overlay and run two floor-collision passes plus ~25 string allocations every physics frame
(`physics.md` puts it at ~3,600 allocations/s), and the first powerup comes at 5 s instead of 15–39 s
(`powerup_spawner.gd:47`). The GDScript VM in a debug template also does more checking.

**Consequence.** The open "~0.5 late frames/s" and A3's 4.10 ms phone figure include that overhead and
cannot be charged to shipping code yet. The search time itself is timed around `schedule_pattern()`
only, so it is less affected than the frame timing is. Not a code bug; the debug build is the right tool
for the `OBSTACLE_SEARCH` log.

**Change.** For the long phone run (next actions 2), take the frame timing (SurfaceFlinger) on a build with
the overlay and freeze log off: a release export, or a debug export with those two vars set false for that
build only. Keep using the debug export for the `OBSTACLE_SEARCH_SLOWEST` log.

### N3 / P3 (latent) — `spike_shard` is only fair at full speed on one real stretch

**Evidence.** Moving the pair tier earlier made `check_placed_pattern_fairness()` fail at seed
2033395789, x=179362: `spike_shard` gives a level-0 player **6 frames** (the bar is 7) at 545, 557, 568,
591 and 613 px/s. Only `spike_shard` failed. As shipped, the pair tier opens at 150 s, which is already
750 px/s, so the gate passes and today's game is fine.

**Consequence.** Any change that opens pairs before 120 s fails the build. That includes HANDOFF's
"Hard = start at tier 3" idea, which is less cheap than it reads. Options when it comes up: keep
`spike_shard` on a tier that opens at ≥120 s (what the reverted experiment did), or tighten the guard.
Never lower `PATTERN_MIN_WINDOW_FRAMES`.

**Change now:** none. Recorded in HANDOFF's tuning notes.

### N4 / P3 — The "stuck @" debug label can show in a release build

`main.gd:297` makes `StuckTimeLabel` visible whenever the stuck watchdog fires, and nothing gates that on
`OS.is_debug_build()`. Shown only after a stall, which is itself a bug, so this is rare. **Change:** gate
it like the other debug UI. **FIXED 2026-10-25**; the console print and the recovery are unchanged.
